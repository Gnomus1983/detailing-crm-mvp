# SaaS Multi-Tenant Plan

Цель: превратить текущую CRM для одного детейлинг-центра в один продукт для многих компаний без переписывания ядра с нуля.

## 1. Что есть сейчас

Текущая рабочая схема проекта:

- `profiles`
- `clients`
- `services`
- `leads`
- `lead_events`
- `attachments`
- `automation_runs`
- `rate_limit_events`
- `client_accounts`

Сейчас логика построена как single-company CRM:

- роли работают внутри одного общего пространства;
- услуги, заявки, клиенты и мастера относятся к одной бизнес-среде;
- RLS завязана в основном на роль пользователя (`owner / manager / detailer`) и на назначение заявки мастеру.

Это хорошо для первого центра, но недостаточно для SaaS.

## 2. Что нужно сделать архитектурно

Нужно ввести слой компании.

Минимальные новые сущности:

### `companies`

- `id uuid primary key`
- `name text not null`
- `slug text unique not null`
- `status text not null default 'active'`
- `contact_phone text`
- `contact_email text`
- `timezone text default 'Europe/Chisinau'`
- `plan_code text default 'starter'`
- `created_at timestamptz default now()`
- `updated_at timestamptz default now()`

### `company_members`

- `id uuid primary key`
- `company_id uuid not null references companies(id) on delete cascade`
- `user_id uuid not null references auth.users(id) on delete cascade`
- `role text not null check (role in ('owner','manager','detailer'))`
- `is_active boolean not null default true`
- `created_at timestamptz default now()`

Зачем отдельная таблица членства:

- один человек сможет быть в нескольких компаниях;
- роли можно будет хранить по компании, а не глобально;
- это правильнее для SaaS, чем один `role` на весь `profiles`.

## 3. Какие существующие таблицы надо связать с компанией

Добавить `company_id uuid not null` в:

- `profiles` или оставить профиль общим, а роль вынести в `company_members`
- `clients`
- `services`
- `leads`
- `lead_events`
- `attachments`
- `automation_runs`
- `client_accounts`

Дополнительно стоит подготовить:

- `company_settings`
- `company_billing`
- `company_integrations`

Но это можно делать вторым этапом.

## 4. Как лучше перенести роли

Сейчас:

- `profiles.role`

Для SaaS лучше:

- `profiles` хранит только общие данные пользователя
- `company_members.role` хранит роль пользователя внутри конкретной компании

То есть:

- `profiles`: имя, email, avatar, общие данные
- `company_members`: owner/manager/detailer в компании A

Это снимет много будущих ограничений.

## 5. Как должна работать авторизация

После логина система должна определить:

1. в каких компаниях состоит пользователь
2. если компания одна:
   сразу открывать ее CRM
3. если компаний несколько:
   показать экран выбора компании

Внутри приложения должен появиться `activeCompanyId`.

Все запросы должны читаться и писаться только в контексте `activeCompanyId`.

## 6. Как менять RLS

Сейчас RLS в основном опирается на:

- `auth.uid()`
- `profiles.role`
- `leads.assigned_to`

Для SaaS RLS должна проверять:

- принадлежит ли пользователь компании записи
- какая у него роль в этой компании

Базовая идея:

```sql
exists (
  select 1
  from public.company_members cm
  where cm.user_id = auth.uid()
    and cm.company_id = leads.company_id
    and cm.is_active = true
)
```

А затем уже поверх:

- owner/manager читают и управляют
- detailer видит только назначенные ему заявки своей компании

## 7. Как мигрировать без поломки live

Самый безопасный порядок:

1. Создать `companies`.
2. Создать одну первую компанию для текущего live-центра.
3. Создать `company_members` для текущих пользователей.
4. Добавить nullable `company_id` в ключевые таблицы.
5. Проставить `company_id` всем существующим live-записям.
6. Проверить выборки и UI на этом этапе.
7. Только после этого сделать `company_id not null`.
8. После этого переписать RLS.
9. После этого переписать frontend на `activeCompanyId`.

Не надо делать это одним большим прыжком.

## 8. Что менять во frontend

Во frontend появится новый контекст:

- `activeCompany`
- `companyMembership`
- `companyRole`

Нужно будет обновить:

- загрузку профиля
- загрузку пользователей команды
- загрузку услуг
- загрузку клиентов
- загрузку заявок
- создание заявок
- настройки
- Telegram-интеграции
- публичную форму `/request`
- клиентский `/status/:token`

Особенно важно:

- `/request` должен создавать заявку только в конкретную компанию
- `/status/:token` должен проверять токен и отдавать данные только внутри нужной компании

## 9. Публичные ссылки для многих компаний

Есть два варианта:

### Вариант A: общий домен

- `app.domain.com/request/:companySlug`
- `app.domain.com/status/:token`

Плюсы:

- проще запуск
- один фронтенд

### Вариант B: поддомены

- `center-a.domain.com`
- `center-b.domain.com`

Плюсы:

- выглядит более серьезно
- удобно для брендирования

Минусы:

- сложнее деплой
- сложнее custom domains

Для начала лучше вариант A.

## 10. Как подключать новую компанию

Операционный сценарий:

1. Создаешь компанию.
2. Создаешь owner-пользователя.
3. Назначаешь owner в `company_members`.
4. Заполняешь демо-услуги или импортируешь их.
5. Настраиваешь Telegram chat id / bot / уведомления.
6. Даешь ссылку на вход.

Это уже можно продавать как:

- подключение CRM
- настройка под центр
- обучение персонала

## 10A. Что подготовить сразу для будущей универсальной платформы

Чтобы потом быстро расшириться с детейлинга на автомойки и шиномонтаж, нужно уже сейчас не зашивать продукт слишком узко.

### Сразу заложить в `companies`

- `business_type text`

Начальные значения:

- `detailing`
- `car_wash`
- `tire_service`

Это не значит, что надо прямо сейчас делать все три режима.
Это значит, что архитектура уже знает: компании бывают разных авто-ниш.

### Что должно быть универсальным

Эти блоки должны остаться общими для всех автоуслуг:

- компании
- пользователи
- роли
- клиенты
- автомобили
- заявки / work orders
- услуги
- оплаты
- уведомления
- история по машине
- отчеты директора

### Что нельзя зашивать жестко под детейлинг

Эти вещи должны стать конфигурируемыми:

- набор услуг
- стадии статуса
- поля в форме заявки
- поля в карточке машины
- чеклист мастера
- тексты клиентского интерфейса
- состав метрик на dashboard

### Что это даст позже

Если детейлинг не полетит, ты не начинаешь новый продукт с нуля.
Ты просто:

- меняешь `business_type`
- подключаешь другой набор услуг
- включаешь другой pipeline
- включаешь нужные поля и экраны

То есть один и тот же SaaS можно переупаковать для:

- детейлинга
- автомоек
- шиномонтажа

без полной переписи ядра.

## 11. Что будет стоить денег при росте

Рост числа компаний увеличивает не “одно число”, а сразу несколько ресурсов.

### Supabase

По официальной странице Supabase:

- `Pro`: от `$25 / month`
- compute `Micro`: `$10 / month`
- Pro включает `$10` compute credits
- значит один рабочий production-проект обычно стартует примерно с `~$25 / month`

Основные расходные зоны:

1. **Database / disk**
   - в `Pro` включено `8 GB`, дальше `$0.125 per GB`
2. **Storage**
   - включено `100 GB`, дальше `$0.0213 per GB`
3. **Egress**
   - включено `250 GB`, дальше `$0.09 per GB`
4. **Edge Functions**
   - `2 million` invocations включено, дальше `$2 per 1 million`
5. **MAU**
   - `100,000` включено, дальше `$0.00325 per MAU`
6. **Custom domain**
   - `$10 per domain per month per project`

Главный вывод по Supabase:

- не надо делать отдельный Supabase project на каждого клиента, иначе compute начнет умножаться;
- для SaaS тебе выгоднее держать много компаний в **одном production project**;
- тогда ты платишь за общий рост данных и нагрузки, а не за отдельный сервер на каждый детейлинг-центр.

### here.now

По официальной `here.now/pricing.md`:

- `Free`: `$0 / month`, `10 GB` storage total
- `Hobby`: `$4 / month`, `500 GB`
- `Developer`: `$20 / month`, `2 TB`

Для твоего фронтенда здесь расход обычно небольшой.

С высокой вероятностью here.now не станет первым узким местом.
Первым упрется именно Supabase:

- база
- storage фото
- трафик
- Edge Functions

### Telegram

В твоем текущем сценарии Telegram-бот как канал уведомлений не выглядит основным источником расходов.
Основная нагрузка идет не на Telegram, а на:

- Supabase Edge Functions
- хранение данных
- frontend hosting

## 12. Как считать деньги заранее

Условный пример:

### До 10 компаний

- 1 production Supabase Pro
- 1 here.now hobby/developer
- без тяжелых фото-архивов

Ориентир:

- Supabase: `~$25-40 / month`
- here.now: `~$4-20 / month`

### 10-30 компаний

Если активно пойдут фото, Telegram, статусные страницы и заявки:

- Supabase все еще может жить на одном проекте
- но может понадобиться рост storage и egress

Ориентир:

- Supabase: `~$25-100+ / month`
- here.now: чаще всего все еще небольшой расход

### 30-100 компаний

Тут уже начнут играть роль:

- фотоархив
- рост клиентов и лидов
- частые Edge Function вызовы
- директорские отчеты

На этом этапе уже нужно:

- мониторить database size
- storage size
- egress
- function invocations
- slow queries

## 13. Самая важная экономическая мысль

Тебе не надо считать:

- “сколько стоит один клиент”

Тебе надо считать:

- “сколько стоит один production stack на 10/30/100 компаний”

Потому что SaaS зарабатывает на том, что много компаний делят одну инфраструктуру.

Если у тебя:

- Supabase + hosting = `50 EUR / month`
- а 10 центров платят по `99 EUR / month`

то у тебя уже хорошая экономика.

## 14. Отдельный кабинет создателя

Если продукт идет как SaaS для многих компаний, тебе нужен не только CRM компании, но и отдельный кабинет создателя платформы.

Это не кабинет директора детейлинг-центра.
Это именно твой внутренний уровень управления сервисом.

### Что это за поверхность

Отдельный экран / кабинет, где ты видишь:

- все подключенные компании
- активные / пробные / пауза / отключено
- текущий тариф
- дату старта подписки
- дату окончания trial
- владельца компании
- контактные данные
- быстрый переход в CRM конкретной компании

### Почему не надо смешивать это с CRM клиента

Потому что у директора центра и у тебя разные задачи.

Директору нужно:

- заявки
- мастера
- касса
- клиенты

Тебе нужно:

- активация компании
- подписка
- статус оплаты
- включить / заморозить доступ
- видеть все компании сразу

Если это смешать, получится грязная и опасная модель доступа.

### Как лучше делать технически

Лучший путь для старта:

- тот же продукт / тот же кодбейс
- отдельный route:
  - `/platform`
- отдельная модель доступа:
  - не через `company_members.role`
  - а через отдельный platform-level доступ

Например:

- `platform_admins`
- или `platform_users`

Это важно, потому что:

- `owner / manager / detailer` — это роли внутри компании
- `platform_admin` — это роль над всеми компаниями

### Что должно быть в первой версии creator panel

Минимум:

1. список компаний
2. `business_type`
3. `plan_code`
4. статус компании:
   - `active`
   - `trial`
   - `paused`
   - `archived`
5. владелец / owner contact
6. дата подключения
7. дата окончания trial / подписки
8. кнопка:
   - открыть CRM компании

### Какие таблицы стоит подготовить

Минимальный слой:

- `platform_admins`
- `company_subscriptions`

Опционально следующим этапом:

- `company_subscription_events`
- `company_billing_notes`

### Какой главный принцип

Сначала:

- отдельный creator panel
- ручная активация компаний
- ручное управление планом

Потом:

- Stripe / автооплата
- инвойсы
- автопродление

То есть сначала операционный SaaS, потом fully automated SaaS.
